# 架构说明（Architecture）

**中文** | English: `architecture.en.md`

这里解释的是那些**从代码本身看不出来**的选择背后的理由。`README.md` 是总览；`DATA_NOTES.md` 存
放测量过程；本文说明**为什么**这些接缝开在它们所在的位置。

---

## 分层

```
config ────────────── 配置：缓存目录、索引目录、模型配置
errors ────────────── 类型化异常体系：PipelineError → Source/Parse/Offline/VectorStore/LLM
logging_setup ─────── 结构化日志输出到 stderr
cache ─────────────── 带 TTL 与 stale-while-error 的磁盘缓存
http ──────────────── 重试、超时、唯一的离线闸门
models ────────────── 各层共享的 pydantic 类型

collectors/ ───────── 每个来源族一个适配器，统一接口
normalize ─────────── record → Document；HTML/实体清洗
synthetic/ ────────── 确定性离线语料与锚点表
textutils ─────────── 归一化、CJK 分词、概念词表、词法打分
dedup ─────────────── 三层去重级联
chunking ──────────── 文档 → 可引用 chunk
embedding ─────────── 哈希（默认）或 OpenAI 兼容，外带磁盘缓存
vectorstore ───────── 混合检索契约：numpy（默认）或 Chroma
retrieval ─────────── 查询规划、检索、时间窗放宽、命中去重
answer ────────────── 抽取式或 LLM 作答、引用、拒答
ingest ────────────── 整条管线唯一运行的地方
serve/app ─────────── HTTP
eval/ ─────────────── ground truth、指标、harness
```

依赖只朝一个方向指。`answer` 知道 `retrieval` 与 `vectorstore`；`retrieval` 知道 `vectorstore` 与
`embedding`；`pipeline/` 里没有任何东西知道 `serve/`。`eval/` 导入 `pipeline/`，而反向从不发生
——harness 是**测量**在跑的那条服务管线，而不是把它重新实现一遍。

## 为什么需要向量库，以及为什么是这一个

**混合，而不是纯向量。** 稠密检索恰好在矿业问题真正依赖的那些词元上很弱：`62% Fe`、
`NI 43-101`、`135,000 吨`、`A$1.2bn`、`碳酸锂`。词法重叠在这些地方很强，而它弱的地方正是稠密
检索强的地方。二者按下式融合：
`(1 - w) · cosine + w · lexical + title_weight · title_match`。

**融合权重是"嵌入器的属性"，不是"任务的属性"。** 学习型模型编码语义，因此稠密相似度是主力，
词法只用来打破平局（`w = 0.35`）。而默认的哈希嵌入器，它的余弦**本身就是**特征哈希后的表面
重叠——在这条路径上两个半边只是同一信号的两个粒度，**更精细的那一半必须主导**（`w = 0.60`）。
测量见 `DATA_NOTES.md`。

**先过滤，再打分。** `kind` / `jurisdiction` / `commodity` / 时间范围都以布尔掩码施加在矩阵上，
因此一个限定"近 7 天的政策"的问题，其 top-5 不可能被价格记录掺进来。**先排序后过滤，正是"你要
5 条却只拿到 4 条"的经典成因。**

**但过滤器只能排除它有判断依据的东西。** 辖区过滤器只排除**确实带有辖区值**的 chunk，因为新闻与
价格的 chunk 都没有——而且，问题里出现的国家通常是**主语**，不是在索取该国的法规全文。

**为什么默认不用 Chroma。** 在 600–900 份文档、几千个 chunk 的规模下，暴力精确余弦只需个位数
毫秒。上 ANN 索引会换来一个依赖、一套持久化格式和一条召回率上的注意事项，代价是换取了没人需要
的速度。`ChromaVectorStore` 存在的意义是让这个接口成为**真实的接缝**而非装饰：**如果只有一个类
实现了某个 Protocol，那这个 Protocol 就只是愿景。**

### 扩展性说明

numpy 后端的每次查询在计算量与内存上都是 O(n)；在 764 个 chunk 的规模下这不算什么。
**首先撑不住的三件事，按先后顺序：**

1. **内存里的矩阵。** 764 × 512 的 float32 是 1.6 MB。到 1000 万 chunk 时就是 20 GB，答案是
   接同一个 `VectorStore` 协议之下的 ANN 索引（`hnswlib` 的 HNSW，或 Chroma/pgvector）。
   其他东西都不用改：`build_store` 就是那道接缝。
2. **Python 层的词法打分。** `NumpyVectorStore.search` 用循环给候选打分，这正是预裁剪存在的
   原因。超过约 5 万 chunk 之后，词法半边应该改成倒排索引（一个真正的 BM25 实现），而不是逐候选
   计算。
3. **加载时重建 `_df`。** 今天是"扫一遍语料"；规模化之后它会变成一个持久化、带版本的产物——而
   随即它也就成了一个**可能与它所描述的 chunk 不一致**的东西，这正是现在不做持久化的原因。

## 去重级联

**从最便宜的一层开始**，因为在一份 749 文档的语料上，昂贵那一层若置于最前，就要跑遍所有配对
（约 28 万次比较），而 LSH 分带只产出几千次。

| 层 | key | 捕获 |
| --- | --- | --- |
| 1 | `Document.id`（规范化 URL + 标题 + 日期） | 完全重复采集 |
| 2 | 规范化标题（同一来源族内） | 跨站转载 |
| 3 | 5-shingle Jaccard ≥ 0.90（经 LSH 分带） | 改写标题 |

它内部的三个决定：

**分带是"跨签名大步长取样"，不是"取前缀"。** 前缀分带永远只哈希同一批 shingle，于是一份低排序
位置被编辑过的文档，可能无法与自己的转载碰撞。**预筛会静默地变成假阴性来源，而不是优化。**

**合并时保留"实质性更长"的那份**（20% 带宽）。没有这个带宽，一条仅仅追加了署名的转载就会顶掉
原始发布方，之后**每一条引用都指向聚合站**。并列时保留先入库者，这让结果**与采集顺序无关**。

**第 1、2 层是全语料范围；第 3 层限定在同一来源族内。** 一份政策公告与一篇新闻完全可能合理地共享
若干样板句，把它们合并会为了二手来源而删掉一手来源。

级联的第 1 层与采集器自己的身份守卫共享同一个 key，而守卫**先跑**，且它存在的原因是另一个（在
底线检查之前让"每来源条数"保持诚实）。这一轮的 `duplicates_by_stage` **两者都报**，因为一个静默
漏掉某一阶段的完备性指标，比没有指标更糟。

## 查询规划：用规则，不用模型

`plan_filters` 用大约八条可读规则抽取时间范围、来源族、辖区与品种。在这里引入一个学习型意图分类器
会给**每一次查询**增加延迟，并且让一个错误的过滤**无法解释**。规则确实会出错；出错时它是一行修复，
推理过程在 git 历史和 `DATA_NOTES.md` 里：

- **主题**词不是**体裁**约束（`"quota"`、`"跌"`）；
- **国家**通常是主语，不是范围；
- 字段未设置意味着"不加约束"，**而不是**"什么都不匹配"。

规划器的输出会在 API 响应里回显，因此用户能确切看到施加了哪些约束。

**时间窗放宽是唯一的"放松"。** 一个硬性的"近 7 天"裁剪，在窗口确实冷清时会返回空结果，而**空答案
比一条"来自九天前、并说明了自己有多旧"的答案更差**。所以当带过滤的检索结果不足时，会用「窗口
×4」重试，且引用会带上真实日期。辖区与来源族**不会**被放宽：它们是语义约束，忽略它们会产出**关于
错误事物的答案**。

## 覆盖检查

"铂金 (platinum) 最近的价格走势如何" 对价格序列的得分是 **0.46**——**高于**若干真正可答的问题
——因为它与每一篇价格文档都共享"价格/走势"。**没有任何相关性阈值能把这种情况和真问题分开**，
所以作答路径把问题里的品种与 `store.available_commodities()` 比对，品种缺席即拒答。

**从索引（而不是从一张静态清单）读取 `available_commodities` 很重要**：在一次价格采集失败之后，
一个关于镍的问题**应该**被拒答，而不是拿镍的新闻硬答。

它拦的是"品种缺口"，不是"事实缺口"——作用范围说明见 `DATA_NOTES.md` §5。

## 作答，以及 faithfulness 能/不能告诉你什么

两个作答器共用一套接口。抽取式那个是默认路径，且**不是占位桩**：每个字都是对索引中文档的引用，
因此 faithfulness 按构造即为 1.0，该指标在那条路径上是**回归护栏**。LLM 路径产出更好的文字、但
保证更弱——而这正是 harness 要量化的东西。

`build_citations` 是**唯一**创建 `Citation` 对象的地方，两条路径都从同一个 `hits` 列表取数，
因此**谁都无法凭空造出引用**。

系统提示词对三件会让矿业分析师发火的事情要求很严：数字必须连同单位与日期一起引用；必须区分政策、
新闻与价格数据；没有证据支撑的答案必须**拒答而不是猜**。**没有这条拒答条款，一个被问到语料未
覆盖品种的模型会用通用知识作答，而 faithfulness 指标就变成了在测训练数据。**

**这些指标各自意味着什么。** `recall@k` 是**检索**属性，它说明不了文字质量；`faithfulness` 是
**文字**属性，它说明不了检索质量；`correctness` 用来区分"取错了文档"与"把对的文档引错了"——一个
问题完全可以被召回、被忠实引用，**而答案仍然是错的**。只报一个数字会把这件事掩盖掉。

## 服务

**用同步 `def` 端点，而不是 `async def`。** 检索是 CPU 密集的 NumPy，嵌入缓存是阻塞式文件 I/O；
把 handler 声明成 `async` 会让这些跑在事件循环上，**卡住其他所有请求**。同步 handler 跑在
Starlette 的线程池里，而 store 在加载后是只读的，因此并发的 `/query` 无需加锁就是安全的。唯一
可变的状态是 engine 引用，`/reload` 会在锁保护下替换它。

**索引缺失不是崩溃。** 服务照常启动，`/health` 说明为什么不能服务，`/query` 返回 503 并附上修复
方法。如果在 import 期就失败，得到的是一个**疯狂重启的容器**，而不是一个"健康检查会告诉你该跑
什么命令"的容器。

**错误是类型化的。** 一个 `PipelineError` 会变成携带自身信息的 502，而不是光秃秃的 500。LLM 故障
会降级到抽取式答案并给自己打上 `mode: "extractive"` 标签，因此调用方能分辨"这本来就是抽取式部署"
还是"这是降级了"。

**没有鉴权，绑定回环。** 这一点写在配置和 README 里，而不是留到生产环境才被发现。`/ingest`
默认关闭：**一个只读 API 却能被告知重写自己的索引，是一件不该被暴露出去的事。**

## 刻意的省略

- **不用 Agent 框架。** 这条管线的形状是直线；把它包进框架，等于在四个函数调用之上加一个依赖和
  一层间接。
- **不用数据库。** 索引就是三个文件。把 chunk 元数据放进 Postgres，会给一个"**全部意义就在于
  全新 clone 就能跑**"的服务加上运维依赖。
- **不加重排序模型。** 交叉编码器大概能提升召回，但也意味着离线默认路径在无法下载模型时就跑不
  起来。它要接的位置就是 `Retriever` 这道接缝。
- **不做并发采集。** 三个适配器、顺序执行、各带自己的超时预算。离线总耗时不到 1 秒，联网不到
  10 秒；并发能买回几秒，代价是**大量可调试性的丧失**。
